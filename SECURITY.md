# Security

PadDisplay lets a tablet **see your PC's screen and control its keyboard, mouse, touch, pen and game controller input**. Please read what that means before using it on a network you don't trust.

## How it is protected
- **Encryption over Wi-Fi (TLS 1.2).** The picture, the audio, everything typed on the tablet, and the PIN itself travel inside TLS (ECDHE key exchange, AES-GCM), so someone capturing Wi-Fi traffic sees nothing readable.
  - **The PC proves who it is.** On first run it makes a self-signed certificate. The tablet remembers the certificate's fingerprint the first time it connects (and only after the PIN was accepted), like SSH, and refuses a PC that later shows a different one. The tray menu shows the fingerprint, so you can compare it with the one the tablet shows if it ever warns you.
  - **Where the key lives.** The certificate is in `tls-identity.bin` next to `settings.ini`. The private key is in your Windows user's key store under the name `PadDisplay TLS`, marked non-exportable. Software running as your Windows user could still ask Windows to sign with it, as with any key you own; delete the file and the key to start a new identity (tablets will ask you to trust it again).
  - **`requireEncryption=1`** in `settings.ini` makes the PC refuse Wi-Fi connections that are not encrypted. It is off by default so tablet apps from before TLS still work. Turn it on once your tablets are updated: a plain connection exposes the PIN and everything after it to anyone on the network, and with this setting the PC never accepts one. (The updated tablet app itself never falls back to plain over Wi-Fi.)
- **Pairing PIN.** Every connection must send a 6-digit PIN, over Wi-Fi and over USB alike. The PIN is generated per PC and shown in the tray menu. USB is included because the `adb reverse` tunnel is reachable by any app on the tablet, not just PadDisplay. You can turn it off for USB with `requireUsbPin=0` in `settings.ini`, at your own risk.
- **Rate limiting on wrong PINs.**
  - At most 5 attempts per minute from each address, and 20 per minute across all network addresses combined, then a 60 s lock-out.
  - Each failed attempt waits 1 s before the answer, and the PC shows a tray warning.
  - USB has its own limit, so someone on the network can't lock out a USB tablet.
- **The optional audio connection** uses the same TLS, PIN check and rate limits. It carries everything the PC plays, so over USB it is as private as the cable and over Wi-Fi it is encrypted like the picture.
- **Handshakes run on their own threads with a 5 s timeout,** and at most 4 at a time, so an idle connection can't block the server.
- **Admin rights are needed only once,** for the installer (or, with the portable zip, for the driver install from the tray). The scheduled tasks it creates run `pnputil` with fixed arguments: two can only switch the virtual monitor device on or off, and a third (registered only if ViGEmBus is installed) can only switch the game controller driver on. The same step also installs the ViGEmBus driver that ships with PadDisplay, and on Windows 11 the virtual camera (below).
- **The bundled ViGEmBus installer** runs with administrator rights only after PadDisplay checks that it is exactly the file it shipped (a pinned SHA-256) and that its Authenticode signature is valid; anything else is refused. It is the project's final release (1.22.0, BSD-3-Clause, signed by Nefarius Software Solutions), and the repository is archived, so it will not get security fixes.
- **The tablet's microphone and camera are the tablet's decision.** Both switches are off by default and ask Android for the permission. Only the tablet can start them: the PC has no way to ask for the microphone or camera. The microphone captures and sends audio only while an app on the PC records from the virtual microphone, and the camera only while an app on the PC has the webcam open (the PC tells the tablet both; a PC with an older PadDisplay cannot say it for the microphone, which then runs while connected). The tablet shows a "Microphone on / Camera on" label whenever either is capturing. While another app is in front, the session keeps running (unless *Stay connected in the background* is off), so the microphone and camera can go on capturing for the PC; PadDisplay's notification then says "microphone on" / "camera on", and Android 12 and later show their own microphone and camera indicators. Disconnect in the notification stops everything. Both use the same TLS, PIN check and rate limits as the picture, and the PC can refuse them in `settings.ini` (`acceptTabletMic`, `acceptTabletCamera`).

- **The keyboard shortcuts service is optional and does one thing.** Sending a keyboard's system shortcuts (Alt+Tab, the Windows key) to the PC needs an Android accessibility service, which only you can switch on, in Android's settings. It requests no screen content and no events. It asks Android for hardware key events only while PadDisplay is in front, connected, and set to send the keyboard to the PC; it stops asking when the window loses focus, and everything that key event path receives goes to the PC connection and nowhere else. While it is on, Android's permission screen will describe it as able to observe key presses, which is what it is: leave it off if you don't want that.
- **Administrator mode is off unless you turn it on** (tray → *Run as administrator*). PadDisplay normally runs with your normal rights, so the tablet can't control elevated windows. With it on, it can, and so can whoever has the PIN. If you also use *Start with Windows*, or tick *Start PadDisplay with administrator rights when I sign in* in the installer, that registers a scheduled task (`PadDisplay Autostart`) that starts the exe with the highest rights when you sign in, without a prompt. A program that starts that way must not be replaceable by normal software, or whatever replaces it (or puts a DLL next to it) gets administrator rights at the next sign-in. So PadDisplay registers the task only when the exe, its folder and every folder above it can be changed by administrators and Windows alone, which is true in Program Files (where the installer puts it) and false for a copy unzipped into your own folders. Such a copy keeps *Run as administrator*, with a UAC prompt at each start.

- **The installer** (`PadDisplay-Setup-<version>.exe`) runs with administrator rights, copies PadDisplay into Program Files and then runs `PadDisplay.exe` once per ticked box; those steps are the same code the tray menu uses, with the same checks (pinned hashes and signatures before a third-party installer runs). It is not code-signed: Windows SmartScreen will say the publisher is unknown, and you can only check a download against the SHA-256 published with the release. Its uninstaller removes what the installer added and leaves drivers that were on the PC before.
- **Trusting the driver publisher is a choice in the installer** (ticked by default, and only offered together with the virtual monitor). The virtual monitor driver is signed by SignPath Foundation, a signing service for open-source projects, not by Microsoft, so Windows asks before installing it. With the box ticked, the installer adds SignPath Foundation's certificate to the PC's Trusted Publishers store, after checking that the driver's catalog is exactly the shipped file (a pinned SHA-256) and that its signature is valid. **From then on Windows installs any driver package signed by SignPath Foundation without asking**, not only this one; an administrator still has to start such an install. It is what Windows' own question does when you choose *Install* and leave its *Always trust software from "SignPath Foundation"* box ticked. Untick the installer's box to keep Windows' question. Uninstalling PadDisplay removes the certificate again if the installer added it (not if it was there before). ViGEmBus and VB-CABLE are signed by Microsoft's hardware publisher, which Windows trusts by itself, so nothing is added for them.

- **Letting the tablet answer UAC prompts is off unless you turn it on** (tray → *Let the tablet answer UAC prompts in only-screen mode*, shown only when running as administrator). UAC prompts normally appear on the **secure desktop**, which can't be captured, so with the tablet as the PC's only screen they're invisible. With this on, while a tablet is connected as the only screen PadDisplay sets the machine-wide policy `PromptOnSecureDesktop = 0`, so prompts appear on the normal desktop where the tablet can see them. **This weakens UAC for the whole PC while it is active:** every UAC prompt, not just ones you trigger from the tablet, then appears on the ordinary desktop where other software could try to see or click it. PadDisplay restores the previous value the moment the tablet disconnects, when it exits, and at the next start-up if it was killed first (the old value is kept in `secure-desktop.txt`), so a crash won't leave the secure desktop disabled. Leave it off unless you need to answer UAC prompts from the tablet.
  - **Clicking the prompt needs a System-level helper, because the UAC prompt runs above administrator.** The consent prompt is at System integrity, a step above an elevated (administrator) program, so not even PadDisplay running as administrator can inject a click into it — Windows (UIPI) blocks input from a lower level to a higher one. To make the tablet's tap reach it, PadDisplay registers a hidden scheduled task that runs as `LocalSystem` (the same mechanism, and the same `D:(A;;FA;;;SY)(A;;FA;;;BA)(A;;GRGX;;;IU)` descriptor, as the virtual-monitor on/off tasks). While the option above is on and the tablet is the only screen, that task starts a short-lived System helper **inside your session**, which injects the tap. The helper is deliberately narrow: it takes commands only over a local named pipe whose security descriptor admits **only SYSTEM and administrators** (never the network, and never a normal-rights program), it injects **only** while the foreground window is the consent prompt (`consent.exe`) and nothing else, and it forwards **only** a left click or the Enter / Esc / Tab / Space / arrow keys — never arbitrary keystrokes. It exits on its own after about two minutes, and is removed when PadDisplay is uninstalled.
  - **What this means:** whoever holds the PIN can approve an elevation prompt while connected, which is exactly what UAC's secure desktop exists to prevent, so this is the most powerful thing the tablet can do. It is off by default, needs administrator rights and only-screen mode, and the restrictions above (consent window only, click-and-a-few-keys only, local SYSTEM/administrator-only pipe) are what keep "click Yes on a UAC prompt" from becoming "run anything as System". Leave it off unless you need it.

## Known limitations
- **The virtual camera is a system-wide, administrator-installed component.** The one-time setup copies `PadDisplayCamera.dll` to `Program Files\PadDisplay\Camera` (writable only by administrators, because Windows' Frame Server service loads it), registers its COM class in `HKLM` and creates a camera visible to every user and every app on the PC. Frames pass through a shared-memory area that any signed-in user's program can write to, as with any virtual camera: another program on the PC could show its own picture in your webcam apps, or read the picture while an app is using the camera. To remove it, uninstall PadDisplay or run `PadDisplay.exe --remove-camera` as administrator.
- **The PadDisplay Microphone is a kernel driver, installed only when you ask for it** (tray → *Install microphone driver (admin)*; not part of the general setup). It is loaded only while PadDisplay runs with *Accept the tablet's microphone* ticked in the tray menu: ticking it enables the device, and unticking it or exiting PadDisplay disables it again, once no app is recording from it (it is never switched off under a recording: Windows would leave the device stuck until a restart) (two more hidden scheduled tasks run `pnputil` as SYSTEM with fixed arguments, so they can only enable or disable this one device, like the virtual monitor's). It is a small KMDF/ACX audio driver ([acxmic](https://github.com/NezucloudResearch/acxmic), its own repository, included as the git submodule `host/third_party/padmic`) that shows one recording device and keeps a 100 ms buffer of audio. PadDisplay.exe feeds it through a control device (`\\.\PadDisplayMic`) that only one program can open at a time and only SYSTEM, administrators and interactive users may open. It has no other interface: it reads nothing from the PC, and a program that opens it can only put sound into the microphone. A bug in any kernel driver can crash Windows, which is why it is separate, optional, small and removable (tray → *Remove microphone driver (admin)*). Windows with Secure Boot loads only drivers that Microsoft has signed; a build without that signature is refused (see [acxmic's signing notes](https://github.com/NezucloudResearch/acxmic/blob/main/docs/SIGNING.md)), and PadDisplay does not turn off Secure Boot or enable test-signing. Where Windows will not load it, PadDisplay uses VB-CABLE instead (next point).
- **VB-CABLE, a third-party driver that comes with PadDisplay, is installed only after you say yes** (the installer's *The tablet's microphone* box, or later a prompt when you tick *Accept the tablet's microphone* or the tablet asks for its microphone; one administrator prompt). It is VB-Audio's unmodified package in `driver\vbcable`; before anything runs elevated, PadDisplay checks the installer, the driver, its catalog and its INF against pinned SHA-256 hashes and checks the installer's signature, and refuses on any difference (tested). It then runs `VBCABLE_Setup_x64.exe -i -h` (VB-Audio's switches for an install without a window). The driver is signed by Microsoft (WHQL), so it loads with Secure Boot. PadDisplay's uninstaller removes it only if PadDisplay installed it (it then runs the same checked installer with `-u -h`); a VB-CABLE that was there before stays, and VB-Audio's own uninstaller removes it at any time. The cable carries only the audio the tablet sends; the host plays it into the cable's playback device like any app would.
- **A tablet that knows the PIN can put sound and pictures into your PC's apps** (a call, a recording) through the virtual microphone and camera, if you allow them. Turn them off in `settings.ini` if you don't use them. Any program running as a signed-in user on the PC can do the same to the microphone by opening the control device while PadDisplay is not using it.
- **Some connections are not encrypted.** USB (it never touches the network) and tablet apps from before TLS (v0.3.0 and older) use plain TCP, so anyone who can capture that traffic sees the screen and everything typed, passwords too. Update the tablet app and set `requireEncryption=1` to refuse plain Wi-Fi connections.
- **The first connection from a tablet trusts the PC it finds.** If someone on your network answers instead of your PC the very first time (before the tablet has remembered the fingerprint), the tablet cannot tell, and they would see the PIN you type. After that first connection the tablet refuses any other PC. Pair on a network you trust, and compare the fingerprint in the tray menu with the one in the tablet's warning if it ever shows one.
- **Whoever has the PIN can type on your PC,** not only move the pointer: a paired tablet's keys are injected as real keystrokes. Don't share the PIN.
- **The PIN is short.** With the rate limits above, guessing it takes on average weeks of continuous attempts, and the tray warns you when it happens. Don't expose port 27183 to the internet.
- **Other Windows users on the same PC** can reach the local port. On a shared PC, keep the USB PIN switched on.

## Reporting a vulnerability
Please **don't open a public issue** for security problems. Use GitHub's private vulnerability reporting instead (repository → *Security* → *Report a vulnerability*), with steps to reproduce. I'll respond as soon as I can.
